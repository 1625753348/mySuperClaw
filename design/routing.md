# 意图路由与模型调用策略

路由分两次决策。第一次在 Intent Engine 内选择识别策略，使用归一化复杂度。第二次在参数校验与业务准入之后选择执行模式，按目标是否需要动态编排判断。L0～L3 按需理解，L4 只规划已经接纳的开放目标。

## 三个独立的判断

| 判断 | 输入 | 用途 |
| --- | --- | --- |
| 归一化复杂度 `complexityScore` | 规则是否命中、表达歧义、候选数、历史依赖、参数缺口、预计步骤依赖 | 选择规则、检索与模型调用策略，范围为 0 到 1 |
| 匹配置信度 `matchConfidence` | 经校准的候选匹配结果，并检查第一与第二候选是否难以区分 | 决定能否采纳候选。低置信度或缺参时进入复核或澄清 |
| 权威风险和权限 | 业务动作、实际参数、租户规则、主体与工具版本 | 决定允许、拒绝、用户确认和审批。服务端策略按当前状态评估 |

复杂度先由廉价特征计算，规则命中、格式、候选检索结果和显式上下文信号即可提供输入。评分配置管理特征权重、归一化方法和模型版本，日志保留用于复判的版本与证据摘要。规则和 Semantic Router 可先形成候选片段；有多个可独立处理的目标时，再分别按候选评估。L2 可以帮助拆分混合输入。每个新 Turn 都重新做识别，候选历史仅提供滞回依据。

## 四档识别策略

Input Normalizer 之后的 Routing Strategy Selector 读取版本化路由规则表。规则表是配置，`intent.routing_assessment` 保存每次应用配置后的评估结果。规则命中或检索得到明确候选时，从对应分支直接产出 IntentCandidate。大模型由高分、滞回选中的模型策略、混合默认路径或允许升级触发。L3 再按候选的历史关联需求进入 Assembler 和 Resolver。[架构图中的四路分支](architecture.md#分层与产物)

显式 `skillKey`、已注册的 SOP 命令或表单动作，可走 L0 的确定规则，以 Skill 版本生成候选。自然语言发现同一个 Skill 时按需要使用 L1/L2，续轮定位待补参 Task 时按需用 L3。Skill 的匹配方式会影响识别路径，执行模式由发布的流程定义与准入决策决定。[SOP Skill 设计](skills.md)

| 层 | 归一化分 | 如何处理 | 与 L0～L4 的关系 |
| --- | --- | --- | --- |
| 规则层 | `0 ≤ score < 0.30` | 条件明确、表达稳定时，用规则、状态机或权限表确定处理入口。缺少确定规则时先检索或澄清 | 以 L0 为主，需要历史关系时用 L3 的确定性路径 |
| 检索 + 小模型层 | `0.30 ≤ score < 0.50` | 用 BM25、向量召回和可选小模型获得候选。足够确定、参数完整且策略允许时可从业务路由直接进入执行 | L1 为主，按需执行 L3；复杂参数可升级 L2 |
| 混合层（滞回区间） | `0.50 ≤ score < 0.70` | 保持上一次可比且仍适用的识别策略。无可用历史时走「检索召回 → 精排 → 大模型辅助判定」 | L1 检索、按需 L2 和 L3。采纳候选前仍核对关系和约束 |
| 大模型层 | `0.70 ≤ score ≤ 1` | 用大模型理解混合意图、拆分候选、辅助提参或选工具。获准且需要动态任务图时调用 Planner | L2 深度理解、按需 L3；执行模式为 PLAN_AND_EXECUTE 时才调用 L4 |

**极高风险优先使用确定性路径。** 可信规则在入口识别出极高风险动作时，不调用大模型，按权限表和状态机直接进入拒绝、确认、人工审核或已批准的固定流程。若先用模型理解了模糊输入，随后识别出极高风险，立即切换到确定性风险处理。普通候选置信度高时，仍需定义、必填字段、授权和审批校验。ToolGateway 再核对实际工具、参数和当前权限。高风险写入按批准的业务流程派发。首期检索可用 BM25 或关键词召回，启用向量服务后再混合排序。

## 滞回如何稳定路由

只有处于 `[0.50, 0.70)` 时，才可以参考同一租户、会话、主体和业务候选的最近可比较判定。比较范围绑定业务目标、目标 Task 及可用输入版本、意图定义、评分配置和安全策略上下文。使用此前 Turn 的记录，避免并发请求借用后续判定。若候选改变、用户换目标、版本变化、策略变化、上次是极高风险覆盖，或上次路径的前提已经不成立，就重新判断。任何时候都重新验证候选和授权。

沿用的是**识别策略**，例如继续使用检索加小模型，或继续使用大模型辅助理解。实际参数、目标标识、准入结论和工具授权由本轮重新得出。离开滞回区间后，按所在档重新选择。

| 多轮变化 | 判定 |
| --- | --- |
| 同一业务候选 `0.48 → 0.55 → 0.64` | 首轮选检索 + 小模型；之后仍符合比较条件，继续走该识别策略 |
| 同一业务候选 `0.71 → 0.68 → 0.49` | 首轮选大模型；中间一轮在滞回区间维持策略；第三轮回到检索 + 小模型 |
| 首次遇到 `0.58`，或从订单查询切换到退款 | 重新执行检索、精排和模型辅助判断。退款准入、固定流程和审批独立评估 |
| 极高风险动作，复杂度 `0.82` | 可信风险规则命中后交给确定性处理，评分保留作审计 |

## 从识别到执行

1. L0/L1 处理明确命令、闲聊或业务候选，复杂输入调用 L2。L3 按需判断每个候选和历史任务的关系。
2. 业务候选按定义补齐和校验输入，形成 Validated Intent IR，经 Policy Engine 决定是否接纳。
3. Execution Router 按目标选择模式。可映射到单步查询就走 DIRECT。命中已发布流程就走 WORKFLOW。只有需要根据目标和中间结果动态拆解的任务进入 PLAN_AND_EXECUTE。用户可在同一轮触发多种模式。
4. L4 Planner 使用已批准目标和允许的工具版本提议 DAG。计划校验、工具最终授权、异步等待和恢复分别由 Runtime 与 ToolGateway 负责。

例如「先把订单 SO001 的退款进度告诉我，再解释为什么本季度退货率上升」可能整体超过 0.70。L2 拆出两个候选，退款进度查单可以走 DIRECT，开放式原因分析走 PLAN_AND_EXECUTE。复杂的退款描述即使需要 L2 提参，实际退款仍走 WORKFLOW。[完整执行模式表](architecture.md#按请求类型选择执行模式)

## 持久化与验收

`intent.routing_assessment` 保存归一化复杂度、匹配置信度、分档、实际识别策略、评分配置版本、风险覆盖标记、原因码与可选的前次记录引用。候选前可先记录 Turn 级评估，拆分后记录候选级评估。比较键包含适用范围的摘要，读取前结合本轮可信版本和状态复核。Redis 可缓存最近比较结果或检索候选，缓存缺失时回 PostgreSQL。准入与执行模式仍保存在 `intent.route_decision`。审计只记录派生分数与原因码，聊天正文和模型提示按各自的持久化策略处理。

评审验收覆盖 0、0.30、0.50、0.70 和 1 的边界，同一候选在滞回区间的双向变化，无历史降级路径，换目标时重新判定，置信度不足时澄清，极高风险覆盖，以及高分多意图中各候选独立选执行模式。
